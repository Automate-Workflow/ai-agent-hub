# CP-030: sandboxing

![safety_and_security](../../assets/icons/safety-and-security.svg) ![intermediate](../../assets/badges/intermediate.svg) ![active](../../assets/badges/active.svg)

**Category:** `safety_and_security` | **Difficulty:** `intermediate` | **Confidence:** `high` | **Status:** `active` | **Verified:** `2026-11-11`

## Definition

Executing untrusted model-generated code, shell utilities, or browsers inside isolated compute boundaries with restricted filesystem, process, and egress access.

## Why It Matters

Sandboxing contains prompt-injection payloads and buggy generated code so faults cannot compromise host infrastructure or private networks.

## How It Works

Ephemeral microVMs, gVisor containers, or isolated OS sandboxes enforce CPU, memory, timeout, filesystem, and outbound network policies.

## Example

Spawning a fresh network-restricted E2B sandbox for each user coding session and destroying it after completion.

## Common Mistakes

Assuming local Docker defaults without dropping Linux capabilities or blocking internal cloud metadata IP egress provides strong isolation.
